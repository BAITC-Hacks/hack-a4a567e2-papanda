# DialecticAI: план адаптера, без реализации проверки

Состояние: исследование исходников 2026-09-21. Семантический разбор пользователь
хочет построить совместно, по шагам. Ни цепочка, ни проверочные промпты здесь
не определяются. Основной репозиторий не читался и не изменялся.

## Общая граница

OpenAI Agents SDK один раз создаёт базовый Draft. Оба проверяющих модуля получают
одинаковые исходное обращение и неизменяемый снимок Draft. DialecticAI запускается
как отдельная задача проверки этого входа; он не заменяет базового агента.

Источник исследования: `../../framework-complete/`, только чтение. Ссылки ниже
даны относительно этого каталога и описывают фактически прочитанный код.

## Что уже совместимо

- `core/llm.py:30`: BaseLLM имеет async generate(messages, tools=None) -> str.
  Небольшой адаптер может передавать эти сообщения в общий Agents SDK gateway.
  Сам runtime умеет текстовые JSON proposals, native tool calling не обязателен.
  Gateway.text принимает instructions/payload, поэтому messages нужно сохранять
  как структурированный payload без потери ролей, а не склеивать произвольно.
- `engine/executor.py:40`: DialecticalEngine принимает agent, logger, validator
  и явные ограничения времени/итераций. Каждый вызов должен иметь собственные
  agent/engine/logger: повторные конкурентные run одного engine запрещены.
- `core/schema.py:44`: AgentInput позволяет передать задачу проверки и metadata.
  Обращение и базовый ответ — входные данные, не успешные Observation.
- `core/tool.py:83`: узкий ObservationTool может читать только переданный снимок.
  `Evidence` из `core/schema.py:70` отделяет результат инструмента от интерпретации.
  Такое чтение доказывает лишь содержание снимка, не правильность ответа и не
  фактическую запись на консультацию, выдачу справки либо ремонт Wi-Fi.
- `core/world.py:106`: предложенный скачок отделён от ASSESS_LEAP; для подтверждения
  требуется успешная практика текущего roadmap. Это соответствует необходимости
  повторной проверки после попытки разрешения, но предмет практики нужно согласовать.

## Существенное несовпадение контрактов

В текущем фреймворке нельзя штатно завершить путь «противоречие не обнаружено»:

1. `core/runtime.py:725`: BEGIN_EXECUTION доступен лишь после создания resolution.
2. `core/proposal_schema.py:164`: contradiction_ids и resolution_ids требуют
   минимум один элемент.
3. `core/world.py:32`: COMPLETE запрещён в фазе planning; `core/world.py:123`
   требует успешные наблюдения исполнения и оценку выбранных скачков.
4. `RUNTIME_CONTRACT.md` требует построить полную цепочку до любых инструментов.

Это структурное ограничение, а не доказательство противоречия в любом обращении.
Нельзя обходить его выдуманным противоречием, FakeSemanticValidator или считать
исчерпание бюджета подтверждением корректности черновика.

После совместного разбора возможны два честных экспериментальных режима:

- Неизменённый фреймворк: ограничение фиксируется как unsupported/inconclusive,
  качество успешной проверки не заявляется. Сохраняется чистота сравнения с готовым
  runtime, но часть требуемых сценариев он может не поддерживать.
- Явно адаптированная тренировочная копия: согласовать отдельное завершение
  проверки без выявленного противоречия; синхронно изменить схему, разрешённые
  переходы, проверку мира, инструкции и семантического судью. Зафиксировать diff
  и назвать вариант адаптацией, не неизменённым готовым фреймворком.

Не нужно заранее выбирать вариант до определения пользовательской цепочки.
«Проверка после базового ответа» сама по себе world-first не нарушает, если это
новая самостоятельная задача. Но нельзя объявлять события базового агента
исполнением ещё не построенного roadmap проверяющего агента.

## Модель и зависимости

Предпочтительный способ сравнения — BaseLLM-адаптер к общему gateway: один явный
провайдер/модель для сравнимых запусков. Наличие другого провайдера не меняет
базовый Agents SDK и не обязывает применять встроенные клиенты DialecticAI.

`integrations/providers.py` содержит GigaChat, Gemini и OpenAI-совместимые маршруты,
но наличие реализации не подтверждает доступность аккаунта/модели. Не использовать
auto/fallback для сравнения: он способен менять модель между запросами.
`engine/executor.py:324` по умолчанию ищет другого доступного провайдера для судьи.
Поэтому передать LLMSemanticValidator явно с выбранным gateway, зафиксировать
модель судьи; если это та же модель, отметить ограниченность независимости оценки.
Ошибки судьи возвращаются как rejection; сохранить исходную причину, чтобы отличать
семантический отказ от ошибки сети/формата. JSON repair тоже расходует вызовы.

`pyproject.toml` core: Python >=3.10, pydantic >=2, jsonschema, python-dotenv.
Dashboard, API, CLI и отдельные провайдеры адаптеру не требуются. Импорт
`dialectic_ai/__init__.py` меняет кодировку stdout и вызывает load_dotenv(); учесть
это при явной загрузке конфигурации, не читать/логировать значения секретов.

Для локального исследования самый малый путь — внешний исходник с явно заданным
путём и fingerprints версии. Но это не самодостаточная сдача. Для переносимой
тренировочной сдачи после выбора режима — зафиксированный snapshot пакета
`dialectic_ai` внутри training/vendor с происхождением, лицензией, hashes и точным
diff адаптации. Не копировать `.env`, data, traces, dashboard или .git. Не делать
editable install, который создаст egg-info в исходном каталоге. Сейчас ничего
не импортировалось, не устанавливалось и не копировалось.

## Порядок будущей реализации

1. Согласовать первый разбор и смысл исхода «не обнаружено» с пользователем.
2. Определить, какие реальные наблюдения подтверждают разрешение, а какие дают
   только вопрос для уточнения. Вопрос не означает, что пользователь уже ответил.
3. Выбрать неизменённый runtime либо явно задокументированную адаптацию.
4. Добавить BaseLLM gateway bridge и узкие инструменты без внешних побочных действий.
5. Передать явного судью и logger, задать бюджеты; исключить mock fallback.
6. Преобразовать RuntimeResult + RuntimeReadModel в общий CheckResult. Только
   валидированный результат допускается; status=completed ещё не доказывает
   философскую корректность. Timeout/API/invalid output -> error/inconclusive.
7. Прогнать контролируемые симуляции: без противоречия, разрешение с повторной
   оценкой, уточнение, неправильный JSON, отказ судьи, бюджет/timeout. Затем один
   реальный запуск с выбранной доступной моделью. Прогонов пока не было.

## Журналирование

DevelopmentLogger (`core/logger.py:42`) по умолчанию пишет в cwd и не редактирует
секреты. Передать адаптер общего log.emit, а не оставлять дефолтные пути.
Логировать run/message/checker IDs, явные входы и структурированные результаты,
принятые/отклонённые предложения, observations, оценки, краткие обоснования,
время, usage, stop_reason и версии. Поля SDK hidden reasoning не запрашивать и
не сохранять. Исключения редактировать до записи. Снимок графа брать через
`observability/read_model.py:145`, сохранить в каталоге конкретного запуска.

План подготовлен по чтению кода. Исполняемость адаптера, доступность провайдеров
и качество диалектической проверки ещё не проверены.
